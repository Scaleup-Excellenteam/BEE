# Google Autocomplete Project — Updated Team SPEC

## 1. Project Goal

Build an autocomplete system that:

* Loads a corpus of text files in an offline initialization stage.
* Accepts user input in an online stage.
* Finds sentences that contain the normalized query as a substring.
* Also supports at most one allowed edit:

  * substitution
  * insertion
  * deletion
* Calculates a score according to the official specification.
* Returns the best 5 completions.
* Sorts equal-score results alphabetically.

---

# 2. System Lifecycle

The system has two main phases.

## Phase 1 — Offline Initialization

The system:

1. Receives Archive.zip.
2. Extracts the archive.
3. Recursively finds all .txt files.
4. Reads every file line by line.
5. Treats every line as one sentence.
6. Stores the original sentence and metadata.
7. Creates a normalized version of each sentence.
8. Builds the corpus/index.
9. Keeps the initialized index in memory for the online stage.

The corpus/index must be built once.

It must NOT be rebuilt for every autocomplete query.

Conceptually:

text
Archive.zip
    ↓
Extract
    ↓
Recursive file scan
    ↓
Read all sentences
    ↓
Normalize
    ↓
Build index
    ↓
Initialize AutoComplete Engine
    ↓
READY


---

## Phase 2 — Online Completion

For every user query:

text
User input
    ↓
Normalize query
    ↓
Get candidate sentences
    ↓
Verify 0-edit / 1-edit match
    ↓
Calculate scores
    ↓
Create AutoCompleteData
    ↓
Sort
    ↓
Return Top 5


The already initialized corpus/index must be reused.

---

# 4. Shared Data Rules

## Requirement

offset represents the location/line of the sentence inside the source file.

## Team Decision

We use:

text
1-based line numbering


Therefore:

text
first line  -> offset = 1
second line -> offset = 2


---

## original_sentence

original_sentence must preserve the source sentence exactly as it appeared in the file, except for the physical line-ending characters.

For example, if the file contains:

text
Hello, WORLD!!!\n


we store:

text
Hello, WORLD!!!


We do NOT lowercase it.

We do NOT remove punctuation.

We do NOT collapse spaces in the original version.

---

## normalized_sentence

Used only for matching/searching.

It must never replace or overwrite original_sentence.

---

## source_text

### Team Decision

Use a consistent relative path.

Example:

text
Archive/books/hamlet.txt


Do not store machine-specific paths such as:

text
C:\Users\name\Desktop\project\Archive\books\hamlet.txt


This keeps results consistent across team members' machines.

## Official Normalization Requirements

According to the project specification:

1. Ignore case.
2. Ignore punctuation.
3. Collapse repeated spaces between words.

## Important Normalization Decision

The project wording says punctuation should be ignored, but exact punctuation replacement semantics must be fixed by the team.

Example:

text

text

text
hello world


This must be defined once and tested consistently.

### TEAM DECISION

The final normalization behavior must be documented before implementation is frozen.

Once selected:

text

# 13. Candidate Retrieval Contract

This rule is critical.

get_candidates(query) may return extra candidates.

However, it MUST NOT omit any sentence that could legally match the query using:

text
0 edits
or
1 allowed edit


In other words:

text
False positives  -> allowed
False negatives  -> forbidden


Person 2 performs the final verification.

Therefore the index is only a candidate-filtering mechanism.

It must never become the final authority on whether a sentence matches.

---

# 14. Reference Implementation

The first implementation should prioritize correctness.

A valid initial implementation is:

python
class CorpusIndex:

    def __init__(self, records):
        self.records = records

    def get_candidates(self, query):
        return self.records


This is a brute-force reference version.

It may be slow, but it provides a correctness baseline.

---

# 18. Valid Match Types

The query may match anywhere inside the sentence.

The system supports:

text
1. Exact substring match
2. One substitution
3. One extra character in the query
4. One missing character in the query


Maximum:

text
1 edit


More than one edit means:

python
None


---

# 19. Scoring Formula

text
score =
2 × matching_characters
-
edit_penalty


For an exact match:

text
edit_penalty = 0


The incorrect, extra, or missing character earns no matching points.

---

text

For a missing character, the position is the location where that missing character would be inserted into the normalized query.

Example:

text

target:
or not


The missing o would be inserted at position:

text

Therefore the position-5 insertion/deletion penalty applies.

# 24. No-Match Contract

This rule is important:

python
None


is the ONLY value that means:

text
no valid match


Do NOT reject a result merely because:

text
score == 0


or:

text
score < 0


A zero or negative score can still represent a valid match according to the scoring rules.

Therefore incorrect logic:

python
if score <= 0:
    reject


Correct logic:

python
if score is None:
    reject


---

# 25. Multiple Matches in One Sentence

If the same query can match the same sentence in several positions, Person 2 must return:

text

Do not automatically stop after the first possible match.
